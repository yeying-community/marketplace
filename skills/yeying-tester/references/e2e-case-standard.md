# YeYing Tester 端到端测试用例规范

## 用例设计

1. 以可观察的业务结果为验收目标。优先覆盖发布门禁涉及的核心流程、权限与身份角色、跨服务数据一致性以及用户能够恢复的失败。明确选择 API 或 UI 边界。
2. 指定用户角色、测试模式、产品版本、依赖服务、必要配置键及测试数据。使用隔离账号和每次独立的数据标识。定义清理步骤，使断言失败或重试后仍可重复执行。
3. 给每个场景分配稳定 ID，并将它写入文档标题和 Playwright 测试标题。场景存在输入或角色变体时，保持变体标题稳定。用文档的实现路径关联 spec。
4. 对业务结果使用明确断言。创建记录后从独立读取入口核对内容及归属，保存设置后重新加载验证持久化。等待明确状态或事件，使用有界轮询。同一用例中指定哪些响应能证明产品行为。
5. 验证断言能在已知错误行为下失败，例如用受控 fixture 模拟保存后读取不到记录。保留前置条件失败、预期缺陷、跳过、重试和最终结果的区别。记录预期失败的原因和对应缺陷，并在修复后恢复发布门禁。
6. 运行代表目标发布环境的项目批次。记录 Tester 与被测产品 commit、运行模式、实际执行与跳过情况以及证据链接。以同样的用例 ID 回查后续批次。

## Tester 文档模板

将 Markdown 写入 `docs/test-cases/<project>.md`。二级标题定义功能模块，三级标题以大写字母、数字和连字符组成的 case ID 开头，以三位序号结尾。字段名与脑图解析器一致。

```markdown
## 文档管理

### DOC-API-001 创建文档后可以重新读取正文

- 优先级:P0
- 类型:API
- 状态:✅ 已实现 — products/example/tests/documents.spec.ts
- 前置条件:文档服务与数据库就绪，已配置隔离测试账号。
- 步骤:
  1. 使用测试账号创建带唯一标记和已知正文的文档。
  2. 使用返回的文档 ID 从读取接口请求正文。
  3. 在清理阶段删除本批次创建的文档。
- 预期结果:读取接口返回相同的 ID、正文和所有者，清理后测试数据可回收。
```

用例评审时记录需求来源、断言位置、配置依赖、环境阻塞原因和最近执行证据。新增跨产品依赖时同步维护 Tester 的 `local-test-dependencies.json` 和项目依赖图。
